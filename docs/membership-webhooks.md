# Memberships: webhooks and schema

Membership subscriptions use a webhook endpoint separate from Medusa's
standard payment webhook. Both endpoints must remain active.

| Flow | Endpoint | Environment variable |
| --- | --- | --- |
| Standard Medusa payments | `/hooks/payment/stripe_stripe` | `STRIPE_WEBHOOK_SECRET` |
| Membership subscriptions | `/hooks/memberships/stripe` | `STRIPE_MEMBERSHIP_WEBHOOK_SECRET` |

Never replace the standard payment endpoint or reuse its signing secret for
memberships.

## Local development

The local Docker image starts two Stripe CLI listeners automatically: one for
standard payments and one for memberships. Their generated signing secrets are
kept in the container and exported before Medusa starts.

Start the local stack:

```bash
docker compose up --build -d backend
```

The backend container requires `STRIPE_API_KEY` in `apps/backend/.env`. Do not
set either webhook signing-secret variable locally; the container supplies its
ephemeral listener secrets at startup. Inspect the listener logs with:

```bash
docker compose exec backend cat /tmp/stripe-memberships.log
```

If Docker cannot validate the TLS certificate used by your local network, the
container starts Medusa using the configured webhook secrets instead. In that
case, keep using Stripe CLI on the host and configure Docker Desktop to trust
your network's root CA before relying on embedded listeners.

## Stripe Dashboard deployment

Create a new webhook destination in the Stripe Dashboard. Do not edit the
existing destination for `/hooks/payment/stripe_stripe`.

Use this URL:

```text
https://<MEDUSA_HOST>/hooks/memberships/stripe
```

Select only these events:

```text
customer.subscription.created
customer.subscription.updated
customer.subscription.deleted
invoice.paid
invoice.payment_failed
```

Copy the new destination's signing secret to the deployment environment as
`STRIPE_MEMBERSHIP_WEBHOOK_SECRET`, then restart the Medusa backend. Keep
`STRIPE_WEBHOOK_SECRET` unchanged.

When rotating the membership webhook secret, deploy the new value before
removing the old Stripe destination to avoid dropped events.

## Verification

1. Create a membership checkout and confirm its PaymentIntent with a Stripe
   test card.
2. Confirm Stripe delivers `invoice.paid` or
   `customer.subscription.updated` to `/hooks/memberships/stripe` with HTTP
   200.
3. Confirm the `membership_subscription` becomes `active`.
4. Confirm it has an `order_id` and that exactly one Medusa order exists with
   metadata containing `membership_subscription_id` and
   `stripe_subscription_id`.

Stripe retries webhooks. The persisted Stripe event ID and the unique
`membership_subscription.order_id` ensure the first paid membership creates
only one order.

## Membership schema migrations

The SQL in the Membership migration files is generated by MikroORM and is
intentionally kept unchanged once it has been deployed. This section is the
human-readable reference for the schema and the flows that use it.

### Migration timeline

| Migration | Purpose |
| --- | --- |
| `Migration20260728140000` | Creates Membership plans, subscriptions, and Stripe webhook idempotency records. |
| `Migration20260804010000` | Adds an invoice-level operational projection for recurring membership billing cycles and expands subscription statuses. |
| `Migration20260807010000` | Extends Membership Plan billing periods with `weekly` and `biweekly`. |

### Tables

#### `membership_plan`

Defines which Medusa variant is sold as a Membership and its recurring billing
configuration.

| Field group | Fields | Purpose |
| --- | --- | --- |
| Identity | `id` | Membership Plan identifier (`mplan_...`). |
| Medusa catalogue | `product_id`, `variant_id`, `sales_channel_id` | Connects the plan to its product, variant, and organization-scoped sales channel. `variant_id` is unique for active plans. |
| Billing | `billing_period`, `amount`, `raw_amount`, `currency_code` | Stores the billing cadence and the price snapshot used when creating an immutable Stripe Price. Current supported periods are `weekly`, `biweekly`, `monthly`, and `yearly`. |
| Stripe | `stripe_product_id`, `stripe_price_id` | References the Stripe Product and immutable Stripe Price used by recurring checkout. |
| Lifecycle | `active`, timestamps, `deleted_at` | Controls storefront availability and soft deletion. |

The `(sales_channel_id, active)` index makes active plans efficient to query
within an organization. A plan price or period change creates a new Stripe
Price; active subscriptions remain tied to their original Stripe Price.

#### `membership_subscription`

Represents the operational Membership record associated with a purchase or a
Stripe subscription. Stripe remains the billing authority for recurring plans;
this table keeps the Medusa projection and Athletify context.

| Field group | Fields | Purpose |
| --- | --- | --- |
| Identity and plan | `id`, `plan_id` | Membership Subscription identifier (`msub_...`) and its Membership Plan. |
| Renewal | `renewal_type` | `recurring` for Stripe Subscription billing, or `none` for a one-time Membership purchase. |
| Stripe | `stripe_customer_id`, `stripe_subscription_id` | Stripe billing references. They are nullable for one-time purchases. `stripe_subscription_id` is unique when present. |
| Latest operational projection | `order_id`, `payment_id`, `fulfillment_id` | Summary references for the latest successful cycle. Historical recurring cycles live in `membership_billing_cycle`. |
| Athletify tenancy | `organization_id`, `company_id`, `stock_location_id`, `sale_source` | Context copied from the server-to-server checkout request and later copied to the Medusa order metadata. |
| Customer and lifecycle | `customer_name`, `email`, `status`, period fields, cancellation fields | Customer display data, access status, billing period, and cancellation intent/reason. |

The `(order_id, plan_id)` unique index prevents creation of more than one
one-time Membership subscription for the same order and plan. The payment and
fulfillment indexes protect the summary links from being reused accidentally.

#### `stripe_webhook_event`

Stores Stripe event IDs already processed by the Membership webhook.

| Field | Purpose |
| --- | --- |
| `stripe_event_id` | Unique Stripe event identifier used to ignore replayed webhook deliveries. |
| timestamps and `deleted_at` | Standard Medusa persistence and soft-delete fields. |

This table is part of webhook idempotency. It does not contain Stripe secrets,
card data, or full event payloads.

#### `membership_billing_cycle`

Added in `Migration20260804010000`. It records one operational Medusa
projection per Stripe invoice for a recurring Membership.

| Field group | Fields | Purpose |
| --- | --- | --- |
| Stripe identity | `stripe_invoice_id`, `stripe_event_id` | Links the cycle to a unique Stripe invoice and the event that created or updated it. `stripe_invoice_id` is unique. |
| Subscription | `membership_subscription_id` | Parent recurring Membership Subscription. |
| Medusa projection | `order_id`, `payment_id`, `fulfillment_id` | The order, captured payment, and symbolic fulfillment created for that invoice. Each reference is unique when present. |
| Financial snapshot | `currency_code`, `subtotal`, `tax_total`, `total` | Amounts received from the Stripe invoice and represented in Medusa. |
| Lifecycle | `status` | `pending`, `paid`, `failed`, or `action_required`. |

### Feature interactions

```text
Admin Membership Plan
  -> membership_plan
  -> Stripe Product + immutable Stripe Price

Recurring checkout
  -> Stripe Customer + Stripe Subscription
  -> membership_subscription (renewal_type=recurring)
  -> Stripe invoice webhook
  -> membership_billing_cycle
  -> one Medusa order + payment + symbolic fulfillment per paid invoice

One-time Membership order
  -> captured Medusa payment
  -> membership_subscription (renewal_type=none)
  -> symbolic fulfillment for only the Membership line items
```

For recurring memberships, the Stripe webhook first verifies its signing
secret, then uses `stripe_webhook_event` and the invoice uniqueness constraint
to make event delivery safe to retry. It creates or resumes the billing cycle,
and only then creates/reuses the corresponding Medusa order, payment, and
fulfillment.

Orders created from either flow preserve the plan sales channel and Athletify
organization, company, stock-location, and sale-source metadata. That context
is used for organization visibility, Stripe Connect destination routing, and
state-tax resolution.

### Migration rules

- Do not edit a migration after it has run in any shared environment.
- Add a new migration for every schema change.
- Keep this document updated when a migration changes the meaning or
  relationship of a Membership table.
